# Pstack skill collision map

## Question

How should the solo-useful parts of pstack at commit
`799151d91b6e12ee7dbd09f708eec108d7de9b3b` fit alongside the current
`petalas/skills` plugins and the same-name skills installed locally, without
weakening existing safety or authorization rules?

## Decision summary

Keep the existing `petalas/skills` implementations of `commit-guidelines`,
`safe-refactor`, and `fix-all-issues` authoritative. Import pstack's small,
host-neutral leaf skills when they do not collide. Merge useful pstack details
into an existing authoritative skill when they do collide. Rename different
workflows that happen to use the same broad word. Exclude team coordination,
Slack, automated public issue or review replies, Cursor cloud-agent machinery,
and Graphite stack operations.

The extraction also needs one suite-wide rule that no main agent or subagent may
send a message, comment, review reply, email, chat post, or other communication
to another human. Internal subagents may communicate with each other. Agents may
prepare local branches, suggested text, and evidence, but the user performs
human-facing publication. Every child-agent prompt must repeat that rule. This
is stricter than pstack's `principle-never-block-on-the-human`, which permits an
external message after confirmation, and stricter than its shipping workflows,
which post verdicts and edit PR state
([never-block-on-the-human](https://github.com/cursor/plugins/blob/799151d91b6e12ee7dbd09f708eec108d7de9b3b/pstack/skills/principle-never-block-on-the-human/SKILL.md),
[shipping](https://github.com/cursor/plugins/blob/799151d91b6e12ee7dbd09f708eec108d7de9b3b/pstack/skills/poteto-mode/playbooks/shipping.md)).

## Action vocabulary

| Action     | Meaning                                                                 |
| ---------- | ----------------------------------------------------------------------- |
| Import     | Copy the pstack behavior as its own plugin, subject only to packaging.  |
| Merge      | Move selected guidance into an existing authoritative skill.            |
| Rename     | Keep a distinct workflow, but give it a non-colliding name.             |
| Dependency | Call an existing skill instead of repeating its contract.               |
| Precedence | Name the one implementation that wins if two skills could both trigger. |
| Exclusion  | Do not copy this behavior into the solo suite.                          |

Packaging and attribution remain subject to the separate licensing and
provenance decision. This note only resolves behavioral ownership.

## Recommended precedence graph

The host-neutral router should route to one owner for each kind of work:

1. Decision planning: `wayfinder`, then `to-spec` or `to-tickets`.
2. Product language and durable decisions: `domain-modeling`.
3. Module shape: `codebase-design`, optionally executed by adapted `architect`.
4. Bugs and performance: `diagnosing-bugs`, with `tdd` or `regression-test` at
   the correct seam.
5. Behavior-preserving structure: `safe-refactor`.
6. Read-only review: `code-review`, `adversarial-review`, or `blast-radius`.
7. Exhaustive remediation: `fix-all-issues`.
8. Commits: `commit-guidelines`.
9. Prose: `unslop`, plus `technical-writing` when the artifact is documentation.

`prove-it-works`, `show-me-your-work`, `swarm`, and the small principle skills
support those owners. They do not compete with them.

## Extraction order

1. Add and test the permanent no-external-communication contract. Make every
   router and subagent workflow depend on it.
2. Preserve the three current plugins unchanged as the initial authorities.
3. Copy exact or near-exact solo leaf skills, starting with `unslop`, `bro`,
   `technical-writing`, `typescript-best-practices`, `show-me-your-work`, and
   the host-neutral principles.
4. Adapt internal-agent skills: `swarm`, `arena`, `architect`, and
   `adversarial-review`.
5. Merge collision content into `diagnosing-bugs`, `safe-refactor`,
   `codebase-design`, and `commit-guidelines` with their existing safety rules
   as acceptance tests.
6. Build the optional host-neutral router last, after every route has one
   canonical owner.
7. Leave Benny, Slack/team-chat, Bugbot, Graphite, PR commenting, PR opening,
   and automated shipping out of the repository.

## Bottom line

Pstack is best treated as a library of small techniques, not as a suite to
fork wholesale. The solo extraction can copy many leaf files nearly verbatim.
Its value drops if it creates second owners for commits, refactors, reviews,
testing, architecture, or debugging. Keep one authoritative skill for each of
those jobs, route pstack's useful details into it, and delete every path that
would let an agent communicate with another human.
